# 项目四：中文政策问答——从检索到证据核对

这个项目把英文词项演示扩展成一条可以逐步检查的中文问答流程：先检查资料是否可见和有效，再检索、检查冲突、引用原文；最后可选择接入本地模型生成待复核草稿。

完成后应能解释三个不同问题：**找到了什么资料、回答是否有原文支持、回答是否切中了用户的问题。** 三者要分别验证。

先修：会读字典、列表、函数、异常和测试；读过[检索基础](../chapters/05-retrieval.md)与[原始 RAG 实验](02-evidence-rag.md)。先完成前两节，再阅读算法细节。

## 1. 跑一个中文问题

在仓库根目录、已完成 `python -m pip install -e .` 的环境中运行：

```bash
python examples/ask_policy.py "退款审核期限是多少天？" --tenant campus
```

预期答案引用 `refund-review` 的 `2026-09` 版本，包含“七个工作日”。输出中的重要字段：

| 字段 | 要检查的内容 |
|---|---|
| `retrieval` | 排名、BM25 分数、问题词项覆盖率；分数不是正确概率 |
| `citations` | 资料 ID、版本、完整原文，能够回到固定证据 |
| `verification` | 是否允许发布、引用是否存在、语义核对进行到哪一步 |
| `abstained` / `reason` | 是否拒答，以及没有资料、低覆盖率或冲突等具体原因 |
| `mode` / `usage` | 离线摘录还是实际模型调用；离线模式 usage 为 null |
| `latency_ms` | 本次本地执行耗时，包含实际发生的步骤 |

先预测，再改动命令：把 `campus` 换成 `partner`，预期政策变成十四个工作日；换成 `unknown`，预期没有检索结果。问题中的“改用另一个租户”不会修改可信应用上下文。

这些商店和政策都是虚构数据，详见[数据卡](../../data/zh-README.md)。

## 2. 沿着一条问题读代码

[rag.py](../../src/agentlab/rag.py) 的顺序如下：

```text
问题 + 服务提供的租户
    → 状态、租户、日期过滤 → 选择有效版本
    → 中文特征 → BM25 排序 → 覆盖率门槛
    → 同一事项的有效资料冲突检查
    → 原文摘录 / 本地生成
    → 逐项引用核对 → 发布原文或保留待复核草稿
```

从 `answer()` 开始，找到它调用的 `visible_documents()`、`search()`、`verify_claims()`。在纸上写出下列问题对应的分支，然后运行验证：

| 问题与租户 | 要验证的行为 |
|---|---|
| `退款审核是三个工作日吗？` / campus | 不采用已经失效的旧版规则 |
| `发票交付方式是什么？` / campus | 两份有效规则冲突，拒答；top-k=1 也不能隐藏冲突 |
| `旧款耳机保修一年吗？` / campus | 已失效资料不参与排名 |
| `退款审核截止时间使用哪个时区？` / campus | 原文没有时区，当前词项门槛会拒答 |
| `校园商店自提点的地图坐标是什么？` / campus | 当前实现会错误返回营业时间；保留失败进行分析 |

最后一题没有通过。它说明“引用的句子是真实原文”只能证明引用完整性，不能证明选择正确。不要把 `publishable=true` 理解成业务质量保证：当前发布门槛只覆盖来源一致性与已定义的结构规则。

## 3. 中文检索怎样计算

`features()` 将“退款审核”拆成“退款、款审、审核”这样的相邻双字特征；英文按字母数字词处理。少量明确写出的替换规则把“退钱”改成“退款”。文档标题、正文和人工别名共同参与检索。

BM25 对问题中的每个特征计算一个分数，再相加：

```text
idf = ln(1 + (N - df + 0.5) / (df + 0.5))
term_score = idf × tf × (k1 + 1) /
             (tf + k1 × (1 - b + b × 文档长度 / 平均长度))
k1 = 1.2, b = 0.75
```

`tf` 是该特征在当前资料中的次数，`df` 是包含它的可见资料数，`N` 是可见资料总数。罕见特征更有区分力；重复次数增加会逐渐饱和；长度归一化减少长文档单纯因词多而占优。

这里采用带 `1 +` 的非负 IDF 变体；参数和 IDF 形式可对照 [Lucene 9.12.3 的 BM25Similarity 文档](https://lucene.apache.org/core/9_12_3/core/org/apache/lucene/search/similarities/BM25Similarity.html)。教学实现没有 Lucene 的索引、字段长度编码和优化，不能据此声称结果与搜索引擎逐项一致。

词项覆盖率另行计算：命中的不同问题特征数 / 全部不同问题特征数。它只作为一个粗糙门槛。提高门槛可能减少乱答，也可能让正常改述被拒绝，因此应同时看覆盖率和错误率。

本实现没有向量嵌入、重排序模型或自动同义理解。自动检出冲突依赖人工配置的 `fact_key` 和 `value`。新增术语、复杂否定、跨文档推理和未标注矛盾都需要另行设计与评测。

## 4. 运行评测，不只看总分

```bash
python -m agentlab.rag_eval --split dev --output work/zh-dev.json
python -m agentlab.rag_eval --output work/zh-test.json
python -m unittest discover -s tests -p 'test_rag*.py' -v
```

报告有两个配置：相同 BM25 的无覆盖率门槛基线，以及门槛 0.32 的候选。默认 test 为 30 题，包括 21 道可答题和 9 道应拒答题；全部题目均公开。这里的数字是本材料的回归结果，不是线上准确率。

逐题报告包含问题、租户、预期事实、实际检索和引用、拒答原因，以及完整配置、代码和数据哈希。先定位 `zh-041`，检查为什么真实引用仍导致错误，再读下列指标：

| 指标 | 分母与用途 |
|---|---|
| `decision_accuracy` | 全部运行题目；应回答时返回预期版本，应拒答时正确拒答 |
| `answer_coverage` | 全部运行题目；有多少实际发布答案 |
| `answerable_recall` | 可答题；有多少成功回答 |
| `abstention_recall_unanswerable` | 应拒答题；有多少正确拒答 |
| `relevant_answer_precision` | 已发布答案；有多少符合题目标注 |
| `exact_quote_integrity_answered` | 已发布答案；引用是否确实属于该租户的有效原文 |
| `human_review_required` | 全部运行题目；有多少生成结果仍需人工复核 |

通过单元测试表示实现符合当前约定。回归数据中的错误照常保留在评测结果里。不能把“测试通过”写成“所有问题均答对”。

## 5. 可选：让本地模型真正生成草稿

只有明确选择 `local` 才会访问本地服务。第一次使用时按 [官方安装与启动说明](https://docs.ollama.com/quickstart) 安装适合自己系统的 Ollama，打开应用，然后检查：

```bash
ollama --version
ollama list
```

Linux 或没有自动启动服务时，在单独终端运行 `ollama serve`。如果提示端口已被占用，先检查现有服务，不重复启动。`ollama list` 列出本机已有模型；无下载模型时不能直接完成下面的实验。

一个小型接口练习选项是 [qwen3:0.6b 的官方标签页](https://ollama.com/library/qwen3:0.6b)。阅读许可和下载信息、确认本机存储与内存适合后，可以自己执行：

```bash
ollama pull qwen3:0.6b
ollama list
```

这是了解安装和接口的具体例子，不是已经通过本课质量评测的推荐模型。小模型可能返回格式错误、截断或不受支持的声明；保留这些结果。也可以选择本机已有的中文模型，把实际标签填入 `YOUR_MODEL_TAG`。本课程脚本不下载模型，也不自动调用付费服务。

先用一个问题检查连通性：

```bash
python examples/ask_policy.py "退款审核期限是多少天？" --mode local --model qwen3:0.6b
```

连接失败先检查服务是否启动；`local_model_not_available` 先检查 `ollama list` 中的精确标签；内存不足或持续超时时先停止实验、换更小模型或减少任务量，再记录新的配置。需要更多输出时可在评测命令中调整 `--max-output-tokens`，同时保留截断失败和增加的成本。没有合适资源就先完成离线项目，G6 保持待完成。

环境正常后再跑题集；PowerShell 可把下面的多行命令合成一行执行：

```bash
python -m agentlab.rag_eval --mode local --model YOUR_MODEL_TAG \
  --split dev --repeats 1 --timeout 20 --max-output-tokens 384 \
  --max-model-calls 12 --max-total-seconds 180 \
  --output work/zh-local-dev.json
```

[适配器](../../src/agentlab/local_model.py) 调用 Ollama 的 `/api/chat`，传入 JSON Schema 并关闭流式输出；服务器返回的内容仍由应用重新验证。接口和结构化输出说明核对于 2026-10-05：[Chat API](https://docs.ollama.com/api/chat)、[Structured outputs](https://docs.ollama.com/capabilities/structured-outputs)。API 参数能约束输出格式，不能证明回答事实正确。

模型产物按以下规则处理：

1. `claims` 中的每个声明必须附带 ID、版本和完整原文。
2. 引用不存在、版本不对、资料不属于当前可见证据，整次回答拒绝发布。
3. 声明恰好等于引用原文时，可以作为模型选出的原文片段发布；切题性仍需评测。
4. 模型改写的声明即便引用真实，也保存在 `generated_draft`，标记 `semantic_support=requires_review`。最终回答保持拒答状态，防止把“有引用”当成“已核实”。

这条路径确实调用模型生成，而自动发布的边界仍限定在可机械核对的原文。改写不自动发布；要发展为开放生成式问答，必须另行验证语义评估或人工审批流程。HTTP 替身测试不计作真实模型实验。

每题记录模型报告的标签、已验证的本地 digest、可获取的服务器版本、输入输出 token、服务器耗时和客户端耗时。即使返回的生成 JSON 损坏，也保留已取得的用量。未知字段保持 null。只访问 loopback HTTP，不使用环境代理、不跟随重定向；响应有字节上限、生成有 token 上限，客户端有关闭连接的截止时间。关闭连接不能保证服务器立即取消已经开始的推理。

本地地址并不自动意味着本地推理：Ollama 服务也能转发云端模型。适配器在发送问题前检查 `/api/tags`，要求存在所选模型及 digest，拒绝带 `remote_host` 或 `remote_model` 的模型元数据。首次检查会缓存到适配器实例；实验过程中不要更换同名模型标签的指向。这依赖可信本地服务如实返回元数据，不能代替服务器的网络隔离。[本地与云端接口说明](https://docs.ollama.com/api/introduction)、[模型列表](https://docs.ollama.com/api/tags)、[上游 API 类型定义](https://github.com/ollama/ollama/blob/main/api/types.go)说明了这一区别。

完成评测但发生连接、超时或预算错误时，命令返回退出码 2，并保留报告。正常完成的质量评测可以返回 0 且包含答错题，应继续分析报告。当前发布没有真实模型运行成绩；运行上面的命令、保存产物并人工检查后，才能写入自己的实验结果。

## 6. 独立任务与验收

不要先查看同学的实现，按顺序提交以下材料：

**任务 A：加入一个新事项。** 添加“校园商店取消订单的截止条件”、一个旧版本和一个 partner 租户的不同规则。自行写出直接提问、改述、无答案和越权场景，检查过滤后再排名的性质。提交 diff、逐题结果和一个设计解释。

**任务 B：修复地图坐标题。** 不许按 `zh-041` 的 ID 或完整问题做硬编码。选择可解释的方法，例如结构化事项识别、重排序或带拒答的答案选择；写出至少两道不同措辞的新题以及两道应正常回答的题，证明没有靠一律拒答“修复”。报告检索召回和发布覆盖率的变化。

**任务 C：审核生成草稿。** 本地模型可用时跑 dev，再请另一位同学按 `human_review.questions` 检查每项声明：数量、时间条件、例外条件、申请与实际执行。标注 `supported / unsupported / unclear`，附解释及引用。缺少模型时先完成 A、B 和协议故障测试，并明确保留“真实生成未验证”，不要以替身结果替代。

**任务 D：换题复验。** 请另一位同学提出未进入当前数据集的政策问答，先固定代码和判定标准，再运行。把失败保留下来，并说明哪项改动只对已有样例有效。

验收应同时检查：能否独立新增事项；能否解释 BM25 的一条排名；能否复现并修复一类失败；能否区分原文真实、语义支持和问题相关性。只有照抄结果或提高一个总分不算完成。

面试时可以据此讲述“基线为什么会错—如何定义评测—采取哪项改动—引入什么代价”，并展示固定版本的逐题报告。不要把手工小数据集的成绩写成通用 RAG 准确率。
