# 01｜Agent 到底是什么：把目标变成可验证的动作

[首页](../../README.md) · [学习路线](../roadmap.md) · [下一章：模型基础](02-llm-basics.md)

**本章目标：**能用一个业务例子区分聊天、工作流和 Agent，并写出任务成功的验收条件。先修要求：了解函数、循环、HTTP 请求即可。

## 从一个具体任务出发

“解释实验室的设备借用规则”只需要生成答案；“查规则，检查当前库存，为符合条件的申请生成预约草稿”则涉及查询、判断、状态和结果验证。是否用了大模型，并不能单独决定它是不是 Agent。

在本项目中，**工作流（workflow）**的主要路径由代码预先定义；**Agent**由模型在运行时根据目标和观察选择下一步动作。实际系统通常混合两者：外层状态机约束权限与预算，内层模型选择检索词、工具或澄清问题。这个划分沿用 [Anthropic 的架构讨论](https://www.anthropic.com/engineering/building-effective-agents)，它是工程约定，并非全领域唯一的定义。

| 系统 | 谁决定下一步 | 适合的任务 | 主要风险 |
| --- | --- | --- | --- |
| 单次模型调用 | 调用方 | 摘要、分类、草稿 | 答案缺少依据 |
| 固定工作流 | 程序分支 | 规则清楚的审批预检查 | 路径覆盖不足 |
| 模型 Agent | 模型依据观察选择 | 路径事先难以枚举的调查 | 错误动作、循环、成本失控 |

不要把“越自主”当成质量指标。设备预约的金额计算、资格校验和权限判断通常适合确定性代码；识别含糊的设备别名、找到对应规则，才可能需要模型。

## 一个闭环的五个部分

设任务目标为 $g$，第 $t$ 步可见历史为 $h_t$，动作是 $a_t$：

$$
a_t \sim \pi_\theta(\cdot \mid g,h_t),\qquad
o_{t+1}=\mathrm{execute}(a_t)
$$

这里的策略 $\pi_\theta$ 可以是语言模型，也可以含规则。历史不是现实世界本身：库存可能已经变化，工具可能超时，用户可能修改目标。因此，动作后的新观察必须进入后续决策。

1. **目标**：生成预约草稿；草稿包含设备、时间、资格依据。
2. **观察**：库存查询结果、规则版本、工具错误。
3. **动作**：搜索文档、查询设备、提出澄清、返回草稿。
4. **状态**：已查证事实、尚缺信息、剩余预算、当前阶段。
5. **终止条件**：通过验收、缺少必要信息、权限不足或预算耗尽。

[ReAct](https://arxiv.org/abs/2210.03629)研究了推理与环境动作交替的方式。落地时需要保存的是动作、依据和可观察结果；一段漂亮的计划文字，不能证明环境真的发生了变化。

## 把“完成了”改写成断言

对于预约草稿，可以建立下列验收条件：

```python
def accepted(draft, inventory, rules):
    return (
        draft["device_id"] in inventory
        and draft["quantity"] > 0
        and draft["quantity"] <= inventory[draft["device_id"]]
        and draft["rule_version"] == rules["version"]
        and draft["status"] == "draft"
    )
```

这是简化的业务断言，不是完整生产验证器。时间冲突、资格和权限仍需单独校验。关键在于：模型说“预约成功”不算成功，后端存在符合要求的记录才算；如果任务只授权创建草稿，真正提交预约反而属于失败。

验收还要包括禁止发生的事，例如没有覆盖其他申请、没有使用其他用户的数据。功能正确与边界正确必须一起满足。

## 用失败链分析复杂度

假设某任务有 8 个必需步骤，每步在前面均成功的条件下，成功率都是 0.95，且任一步失败都会使任务失败，则整条链成功率是 $0.95^8\approx66.3\%$。这只是说明性计算，并非某个模型的实测值；真实流程可能恢复、分支，也可能存在共同故障。

这个计算说明两个优化方向：减少不必要步骤，以及为可恢复错误设计恢复路径。把四次简单查询合并成一个清晰的只读工具，有时比增加一个“反思 Agent”更有效。增加模型调用之前，应先检查工具接口和验收标准是否清楚。

## 动手练习与答案

为“读取课程公告，生成待办清单”设计三种方案：一次调用、固定工作流、Agent。写出各自必须存在的输入、输出、权限和停止条件。

**参考答案：**公告已给出、只需摘要时，一次调用即可；每天从固定栏目拉取公告、按日期过滤、生成清单，适合工作流；公告中存在附件和交叉引用，需要根据内容选择后续检索时，才有采用 Agent 的理由。三者都应保留公告来源，不应擅自把清单写入别人的日历。

**自评标准（4 分）：**任务边界明确 1 分；方案选择有理由 1 分；结果可验证 1 分；包含失败和终止条件 1 分。只画架构图，没有验收断言，最多得 2 分。

## 面试追问

**“Agent 与普通后端服务最大的不同是什么？”** 后端工程的权限、事务和可观测性仍然需要；变化在于部分控制流由概率模型决定，因此必须约束动作空间，并用环境反馈验证结果。

**“什么时候不该使用 Agent？”** 输入输出和处理路径已经明确、规则必须严格执行、额外模型调用没有可测收益时。先交付可测的最简单基线，再讨论自主性。
