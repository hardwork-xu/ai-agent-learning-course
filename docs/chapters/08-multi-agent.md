# 08｜多 Agent：先证明分工有价值

[上一章](07-planning-and-workflows.md) · [首页](../../README.md) · [下一章](09-evaluation.md)

**本章目标：**判断任务是否值得并行拆分，设计交接契约，并用同预算基线评价收益。

## 角色数量不是系统能力

把一个模型分别命名为“产品经理”“工程师”“审查员”，不会自动产生互补知识。若它们读取相同资料、使用相同模型和相同偏见，可能只是用更多 token 重复同一个错误。

多 Agent 的实际收益通常来自三类结构：不同子任务可以并行；不同任务需要不同工具或权限；上下文过长，需要把相对独立的材料分开处理。[AutoGen 论文](https://arxiv.org/abs/2308.08155)展示了通过多 Agent 对话组织应用的方式；这里讨论的是编排原理，不依赖该框架的具体 API。

例如，为一套开源库写升级报告，可以分别检查 API 变化、依赖兼容性和迁移测试。三个工作包输入明确、证据相对独立，适合并行。相反，“先确定设备，再查该设备库存”存在数据依赖，强行同时执行会造成猜测和返工。

## 并行到底省了什么

假设三个独立只读任务分别用时 8、11、6 秒，串行执行需要 25 秒；并行的理想执行时间是 11 秒，若汇总另需 4 秒，则总时间约 15 秒。这是说明性计算，不是实测基准。

通用表达为：

$$
L_{\mathrm{parallel}}\approx \max_i L_i+L_{\mathrm{coordination}}
$$

但是费用通常仍近似各任务成本之和，再加调度和汇总。限流、资源竞争、长尾任务、失败重试会削弱提速。优化报告要分别写延迟、成本和质量，不能用一个“效率提升”把三者混在一起。

共享模型限额时，应通过并发信号量与任务预算控制请求。总任务有 20 次调用预算，不能给 5 个子任务各 20 次却仍声称总上限为 20。

## 给工作包一个可验收的接口

```json
{
  "task_id": "compatibility-check",
  "goal": "找出目标版本的依赖兼容限制",
  "scope": ["已授权的公开发布说明"],
  "deliverable": {
    "claims": [],
    "evidence": [],
    "unresolved": []
  },
  "limits": {"max_tool_calls": 6},
  "write_access": false
}
```

交接应包含事实、证据位置、未解决问题和失败状态。只有“已检查，一切正常”无法审查，也无法与另一子任务的冲突结果对照。

协调者负责分配互不冲突的范围、合并结果、解决矛盾和决定是否完成。子任务的输出仍是待验证数据，不能因为来自另一个 Agent 就获得更高权限；外部材料中的恶意指令也可能经摘要转发。

## 共享状态带来的新错误

若两个执行器同时读到库存为 1，并分别预约 1 件，即使各自推理都正确，总体仍可能超售。问题来自并发控制，应由事务、版本校验或锁处理。

代码任务可以分文件或目录分工，但共享配置、依赖文件和公共接口仍可能冲突。每个可变对象最好有明确所有者；需要跨范围修改时，通过结构化交接协调，而不是让多个写者互相覆盖。

另外还要处理重复交付、子任务超时、父任务取消以及部分结果。汇总器必须区分“没有发现问题”和“任务没有执行成功”。把失败子任务直接从报告中删掉，会制造虚假的完整性。

## 审查 Agent 不天然独立

让第二个模型审查第一个模型的答案，可能有帮助，也可能受前文结论影响。更可靠的做法是让审查者先看到需求和证据，再按独立标准验证。能通过编译器、测试、数据库约束检查的部分，应优先用确定性工具。

比较多 Agent 与单 Agent 时，至少设置同模型、同工具、同最大 token 或金额预算的基线。若多 Agent 只是用了三倍调用，不能把全部收益归因于“协作机制”。另做去掉角色分工、去掉独立审查的消融，才有助于定位收益来源。

## 动手练习与答案

现在要分析三个互不依赖的开源项目，但最终需要使用统一评分标准。设计分工与合并流程，并处理其中一项检索失败。

**参考答案：**三个只读工作包共用评分定义，各自返回逐项证据、版本和未知项；协调者校验指标口径后合并。检索失败的项目显示“该项待核实”，可以在剩余预算内重试，不能记为 0 分或满分。统一评分标准应在分工前确定，避免事后迎合结论。

**自评标准（5 分）：**可并行性 1 分；统一契约 1 分；证据交接 1 分；失败不伪装为完成 1 分；预算与取消可控 1 分。

## 面试追问

**“如何证明多 Agent 有必要？”** 展示同预算比较、子任务独立性、真实的延迟构成和失败分析。若单 Agent 同样可靠且更便宜，保留单 Agent 是合理工程选择。
