# 协议与框架：理解边界再迁移

[返回首页](../README.md) · [工具调用](chapters/04-tool-use.md) · [多 Agent](chapters/08-multi-agent.md)

一个系统可能同时使用模型 API、编排框架、工具协议和观测平台。它们解决的问题不同，不能仅凭名称判断能力。先画出请求经过的边界，再决定引入哪个组件。

## 四层分工

| 层 | 解决的问题 | 仍需应用负责的内容 |
| --- | --- | --- |
| 模型 API | 输入输出、工具请求、用量返回 | 业务目标、参数语义与预算 |
| 编排框架 | 状态、分支、暂停和恢复 | 状态含义、事务边界、恢复后的权限 |
| 工具协议 | 能力发现、调用和结果交换 | 身份、数据权限、执行副作用 |
| 观测评估 | 采集轨迹、比较实验 | 数据脱敏、指标口径、是否允许上线 |

例如模型提出“创建工单”，编排器安排步骤，协议把请求送到服务；真正的服务仍要检查登录身份、工单所属租户和重复提交。没有哪个中间层天然替业务保证正确性。

## MCP：把工具连接契约标准化

MCP 的 Host 承载应用，Client 连接 Server。Server 可以提供 tools、resources 和 prompts。本节固定使用 **2025-11-25 协议版本**做教学示例，不把该版本称为最新版。新版本可能改变生命周期，升级时应按版本文档迁移。[协议总览](https://modelcontextprotocol.io/specification/2025-11-25)

在该版本中，客户端先通过 `initialize` 协商版本与能力，再发送 `notifications/initialized`，随后才能使用已协商能力。面试中要区分“客户端支持某功能”和“本次连接已协商该功能”。[生命周期规范](https://modelcontextprotocol.io/specification/2025-11-25/basic/lifecycle)

以下是**完成初始化之后**的工具调用消息，用于理解格式，不是可独立运行的 MCP 服务：

```json
{
  "jsonrpc": "2.0",
  "id": 7,
  "method": "tools/call",
  "params": {
    "name": "search_handbook",
    "arguments": {"query": "library hours", "limit": 3}
  }
}
```

工具发现使用 `tools/list`；调用返回内容与可能的工具执行错误。协议错误和业务工具执行错误要分开处理，避免把“工具业务失败”误判成“网络不可达”后盲目重试。[工具规范](https://modelcontextprotocol.io/specification/2025-11-25/server/tools)

### 身份从哪里来

上面的参数故意没有 `tenant_id`。真实服务应从已验证的认证上下文推导主体和租户，再构造查询。允许模型任意指定“自己属于哪个租户”，会把授权权力交给不可信输入。

固定版本的 HTTP 授权规范讨论 OAuth 相关流程；stdio 的凭据处理不同。不要把所有传输都套成同一登录方式，也不要把能建立连接理解为获准调用所有业务动作。[授权规范](https://modelcontextprotocol.io/specification/2025-11-25/basic/authorization)

### 迁移练习

将工具项目的只读查询函数包装成 MCP 工具。先保留原函数与参数验证，再增加协议适配层，最后连接客户端。该适配是扩展练习，仓库没有内置 MCP Server。

验收时检查五件事：版本不兼容时退出；未知工具被拒绝；无效参数没有进入业务函数；取消请求不等于已经回滚副作用；服务端工具描述不能给自己增加权限。可用协议官方 SDK 实现，但应锁定依赖并按对应版本测试。

## A2A：任务委托边界

A2A 关注 Agent 之间的互操作，涉及能力描述、消息、任务状态与产物等概念。可以把一次协作理解为“委托一项任务并获得可追踪结果”。MCP 常用于连接工具与上下文，两者可能共同出现在系统中，不能简单断言互相替代。[A2A 核心概念](https://a2a-protocol.org/latest/topics/key-concepts/)

自行实现 HTTP JSON 接口不代表已经符合 A2A。若声称兼容某协议，应给出版本、消息 schema、认证方式和互操作测试。

## 框架怎么选

原生 Python 的优点是控制流清晰，缺点是持久化与调度需要自己维护。LangGraph 提供状态图和持久执行等编排能力；阅读它时重点对照节点、状态、checkpoint、interrupt 与恢复语义。[LangGraph 官方文档](https://docs.langchain.com/oss/python/langgraph/overview)

Google ADK 是另一种 Agent 开发框架。评估框架时查看工具、会话和运行时接口能否承载既有需求，再决定是否迁移。[ADK 官方文档](https://adk.dev/)

不要凭 star 数做最终选择。针对同一个工单任务写一页 ADR：

1. 约束：是否跨进程恢复、是否多人审批、是否需要已有团队栈。
2. 方案：原生状态机与一个框架，比较实际需要编写和维护的代码。
3. 实验：在提交副作用后模拟崩溃，再恢复，观察重复执行。
4. 决策：哪些收益值得依赖成本，什么时候重新评估。

框架保存 checkpoint，并不自动让远端扣款或发信成为幂等操作。恢复时仍要查业务结果或使用稳定幂等键。

## 面试练习与参考答案

**题目**：团队已有可靠 HTTP 工单 API，是否必须改成 MCP？

**参考**：先确认消费者和问题。如果只有单一后端调用，已有接口足够；若多个 Agent Host 需要统一发现工具和理解 schema，可以增加适配层。业务授权、幂等和审计仍留在原服务。用接入成本、版本兼容和故障处理做取舍，而不是为了“使用协议”重写业务。

**追问**：接入工具后遇到提示注入怎么办？协议传输不等于内容可信。保持资料与指令分离，在执行层约束操作，并用含恶意工具返回的测试验证边界。
