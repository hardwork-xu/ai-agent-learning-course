# 11–20：工具与执行

[题库目录](README.md) · [上一组](01-foundations.md) · [下一组](03-rag-context.md)

## 11. 一个好的工具接口应该包含什么？〔入门〕

**直接回答：** 明确的单一职责、参数 schema、资源范围、返回结构、错误类型，以及是否产生副作用。名称和说明要让调用者知道何时使用，而非只罗列实现细节。

**理由与取舍：** `execute(text)` 把所有责任压给调用者；`lookup_policy(topic)` 更容易校验和测试。粒度也不能无限缩小，否则一次业务动作会需要大量往返。最终依据任务轨迹的正确率与调用次数选接口。

**追问／得分点：** 把一个任意 SQL 工具拆成两到三个受限查询工具，并说明失去的灵活性。

## 12. 为什么不能把模型生成的参数直接传给函数？〔入门〕

**直接回答：** 参数来自不可信输入通道，应先验证工具名、字段集合、类型、范围及资源授权，再执行。

**理由与取舍：** Python 中 `bool` 是 `int` 的子类，简单 `isinstance(x, int)` 可能误收布尔值；浮点数还可能包含 NaN 和无穷。严格验证比“尽量帮模型纠正”更可预测。可修正错误可以返回结构化反馈，但必须限制修正次数。

**追问／得分点：** 为加法工具列出未知字段、布尔参数、超大数、缺失字段四类测试。

## 13. 哪些失败可以重试？〔中阶〕

**直接回答：** 短暂的网络异常、限流和部分服务不可用可按契约重试；权限不足、参数非法、业务状态冲突通常需要更换输入或终止。写操作在结果未知时，先考虑查询状态和幂等机制。

**理由与取舍：** 超时不代表服务端没有执行。重试还会增加负载，应设置尝试次数、整体截止时间与带抖动的退避。上下游同时重试会把请求数乘起来。[AWS 的重试工程指南](https://aws.amazon.com/builders-library/timeouts-retries-and-backoff-with-jitter/)讨论了这些风险。

**追问／得分点：** “创建工单超时”与“查询知识库超时”的恢复策略为何不同？

## 14. 幂等键能解决什么，不能解决什么？〔中阶〕

**直接回答：** 在约定的作用域和保留期限内，同一幂等键及同一请求可以返回原结果，避免一次逻辑动作因重试重复执行。它不能替代身份认证、业务校验或下游系统的幂等能力。

**理由与取舍：** 服务端应把租户、键、请求摘要和结果一起保存；同键异参数必须拒绝。记录与本地副作用要在事务中提交。若调用外部服务后进程崩溃，仅有本地缓存仍可能重复执行，需要下游幂等、对账或 outbox 等机制。[Stripe 的契约](https://docs.stripe.com/api/idempotent_requests)是一个具体实现例子。

**追问／得分点：** 为什么每次重试随机生成新键会失去去重作用？

## 15. 如何防止 Agent 一直循环？〔入门〕

**直接回答：** 在运行时设置最大步骤、总体时间、调用预算与终止状态，检测重复无进展的动作，并为预算耗尽返回明确的未完成结果。

**理由与取舍：** 提示模型“不要循环”只能帮助决策，不能强制停止。仅比较工具名也不够：同一查询换页可能合法；相同参数连续收到同一错误才更像无进展。预算应覆盖参数修正和重试，而不仅是成功动作。

**追问／得分点：** 达到上限时，应该如何保留已完成工作并避免把未完成任务报告成成功？

## 16. 并行调用工具应该满足什么条件？〔中阶〕

**直接回答：** 分支之间没有数据依赖，且资源写入不会产生冲突时才适合并行。只读查询通常较容易并行，库存扣减和审批执行需要更谨慎。

**理由与取舍：** 并行可以降低等待时间，但会增加瞬时负载和合并复杂度。设定有界并发、每个分支的截止时间和部分失败策略；若最终答案依赖所有分支，不能默默忽略失败的一支。

**追问／得分点：** “查政策”和“查账户状态”可以并行；“修改地址”和“按地址计算运费”为什么通常不行？

## 17. 工具调用日志应该记录什么？〔中阶〕

**直接回答：** 记录任务 ID、调用 ID、父调用关系、工具版本、开始和结束时间、脱敏后的参数摘要、状态、错误类别、重试次数与结果引用。

**理由与取舍：** 这些信息用于重建“发生了什么”，无需记录完整秘密或无关原文。只保留最终文本无法定位执行失败；毫无筛选地保存工具返回又会扩大泄露面。日志和业务数据应有独立访问策略与保留期。

**追问／得分点：** 如何在不记录认证令牌的情况下诊断一次权限拒绝？

## 18. 审批应该绑定什么？〔进阶〕

**直接回答：** 审批应绑定具体动作的规范化参数摘要、资源版本、审批人身份和权限、有效期及目标租户。执行时必须重新验证，而不是只存一个 `approved=true`。

**理由与取舍：** 审批之后改了金额、收件人或目标资源，原审批就不应继续有效。审批页面要展示具体后果，不能只写“继续”。并发修改通过版本比较或数据库条件更新处理。

**追问／得分点：** 说明“先批准 A，再把请求改成 B”的攻击如何被阻止；过期审批怎么恢复？

## 19. 为什么“恰好一次执行”很难？〔进阶〕

**直接回答：** 分布式环境里，客户端可能无法区分“服务端未执行”与“执行完成但响应丢失”。没有跨系统一致性协议时，不能靠一次网络请求保证全链路恰好一次。

**理由与取舍：** 常见实现是至少一次投递配合幂等消费，或本地事务配合 outbox，把可证明的保证限制在具体边界内。跨越支付、邮件等外部系统时，还要考虑重复检测和人工对账。

**追问／得分点：** 画出数据库提交后、响应发送前崩溃的时间线，指出客户端应该怎样重试。

## 20. MCP 与 function calling 是同一层的东西吗？〔中阶〕

**直接回答：** 不是。Function calling 通常指模型以结构化形式提出工具调用；MCP 是连接应用与工具、资源等上下文能力的协议。可以通过 MCP 暴露工具，再由模型的调用机制选择使用。协议的能力范围见 [MCP 官方介绍](https://modelcontextprotocol.io/docs/getting-started/intro)。

**理由与取舍：** 协议统一不等于权限统一，也不保证工具内容可信。应用仍需要认证、授权、输入校验、超时和审计。协议版本及 transport 的具体约束应以所采用版本的官方规范为准。

**追问／得分点：** 模型看到了一个工具，为什么不代表当前用户已获准执行这个工具？
