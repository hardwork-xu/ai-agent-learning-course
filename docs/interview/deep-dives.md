## D01：答案引用真实，为什么用户仍说答错了

**场景。** 虚构设备维修知识库包含“保修期”“响应时间”“付费例外”，用户问：“设备过保两个月，周末能上门吗，多久处理？”系统引用了真实的工作日响应条款，却没有回答过保和周末条件。

**怎么推理。** 先把需求拆成可检查的子问题，并写出每个子问题需要什么证据。沿链路检查：原文件是否有答案 → 解析是否保留表头、条件和例外 → 切块是否拆开依赖 → 检索是否召回 → 重排是否挤掉必要证据 → 生成是否覆盖所有子问题。引用完整性只能证明出处，不能替代相关性和覆盖率。

切块先保留标题、条款范围、表头和来源版本，再控制长度；重叠能缓解边界丢失，也会增加重复。精确型号/错误码适合词项匹配，口语改写可尝试向量检索。先在相同语料、权限、候选数量和查询上比较单路、混合与重排，不预设复杂方案一定更好。RRF 按排名累加 `1/(c+rank)`，避免直接混合不可比的原始分数；它仍会丢掉分数间隔信息，候选窗口和 c 仍须在开发集选择。[Elastic RRF 文档](https://www.elastic.co/docs/reference/elasticsearch/rest-apis/reciprocal-rank-fusion)

**追问。** 两份必需证据都在 top-10、只一份在 top-3，该调哪里？权限先过滤后发现某类查询召回下降，能否把未授权片段放进模型再要求它保密？为什么一次增加 chunk、top-k、重排模型和 prompt 后无法归因？

**动手与验收。** 先运行 `python docs/interview/exercises/02_rrf.py`，阅读[中文检索项目](../projects/04-chinese-rag.md)。独立新增 12 条合成问题：精确标识、同义问法、跨条款、缺失证据各 3 条。对每题保存必需证据 ID、召回列表、回答覆盖的子问题。报告 Recall@k 的相关证据分母，以及“全部必需证据都召回”的查询比例；两者不能混用。更改切块后保存 source ID、revision、offset 与内容 hash，证明能回到原文。练习数量只是覆盖要求，不是泛化结论。

**常见失分。** 只答“换更大 embedding”；把非零相似度当作有答案；只展示一条成功问答；把 RRF 练习程序称为已经完成向量检索。来源线索：N01。

## D02：什么时候让模型决定下一步

**场景。** 同一个维修系统有两类任务：提交已有表单；诊断“设备偶尔掉线”并决定查状态、查历史还是补问用户。业务方希望全部改成多 Agent。

**怎么推理。** 先区分可预先确定的流程和需要依据新观察调整的决策。表单验证、审批和落库用显式状态机容易审计；诊断可能需要模型在有限工具集中提出下一步。模型负责提案，执行层负责鉴权、校验、预算和副作用。多角色文本对话没有天然收益，还增加消息、上下文和排障成本。工作流与动态工具决策的区分可参考 [Anthropic 架构说明](https://www.anthropic.com/research/building-effective-agents)；该文章是设计参考，不是当前框架功能表。

先实现规则流程基线和单一决策者，再用相同任务比较完成率、额外提问、工具调用、耗时与审核量。需要多个专业上下文、可并行的独立子任务或权限隔离时，再提出拆分方案。是否采用取决于任务收益，不取决于 Agent 数量。

**追问。** 一次规则命中为什么也被叫 Agent？工具返回“设备不存在”后，下一步由谁决定？计划写得很长但没有执行记录能证明什么？

**动手与验收。** 运行 `python -m agentlab demo tools`，阅读 [runtime.py](../../src/agentlab/runtime.py) 与[工具项目](../projects/01-tool-agent.md)。给自己的应用设计三类合成诊断：缺少设备 ID、状态接口返回新故障码、无权限读取历史。提交决策表与轨迹，至少有两种观察导致不同下一步；没有观察的固定脚本必须标注 scripted。真实模型接入另存模型、版本、请求预算和结果，不能把 scripted planner 当作模型能力证据。CaseDesk 的[执行引擎](../../src/agentlab/desk/engine.py)与[规划器](../../src/agentlab/desk/planner.py)提供工单查询、知识检索、补问和结束动作的参考边界；阅读后仍需用自己的新任务证明决策收益。

**常见失分。** 只画 Planner/Executor/Critic 三个框；把审批交给另一个模型就声称完成授权；没有基线却宣称复杂度带来提升。来源线索：N03、N05、N08。

## D03：JSON 合法，工具为什么仍不能执行

**场景。** 模型提出 `create_repair`，JSON 可以解析，字段也齐全，但设备属于另一个租户，预约日期已过期，正文还有“已获管理员同意”。

**怎么推理。** 分四层检查：解析层限制大小、重复键和非有限数；schema 层检查必需字段、类型、枚举和额外字段；业务层检查设备、时间、状态、金额或配额；授权层从认证身份推出租户、角色和可执行动作。模型不能通过填写 `role` 或“已批准”获得权限。JSON Schema 的 `properties` 不会自动要求字段存在，也不会自动拒绝未知字段，要明确配置 `required` 与 `additionalProperties`。[JSON Schema 对象规范说明](https://json-schema.org/understanding-json-schema/reference/object)

返回给模型的错误应当足以修正用户输入，但不泄露其他租户是否拥有某设备。schema 失败可以有限修正重试；权限失败不能通过不断改参数绕过。工具描述与结构化输出帮助表达，服务端检查才决定执行。

**追问。** Python 中 `True` 能否当作数量 1？同一个 JSON 出现两个 `priority`，不同解析器会不会产生不同审批内容？模型声称“工具成功”但回执缺失，该信谁？

**动手与验收。** 运行 `python docs/interview/exercises/01_dispatch.py` 和 `python -m unittest discover -s tests -p 'test_quality.py' -v`。独立为一个新工具补充正常、未知字段、重复键、错误类型、越权、陈旧版本六组契约测试，检查失败时数据库没有副作用。提交 schema、执行层检查位置和失败映射表，不只提交 prompt。CaseDesk 的[HTTP 输入与鉴权边界](../../src/agentlab/desk/api.py)及[独立安全回归](../../tests/test_desk_security.py)可作为反例入口，检查请求方是否有机会篡改身份。

**常见失分。** “用了 function calling 就保证正确”；把所有工具名动态映射到任意函数；用模型自述作为业务完成信号。来源线索：N02、N03。

## D04：用户取消后，任务为什么还在花钱

**场景。** 一次诊断预算 30 秒；检索用了 4 秒，模型调用和重试用了 18 秒，剩余工具仍拿到默认 20 秒超时。用户关闭页面后，后台继续执行。

**怎么推理。** 单次进程内用单调时钟计算剩余预算；需要跨重启恢复时，另存可恢复的截止时间，并明确系统时钟调整的处理方式。下游拿到的是剩余预算。上述时刻最多剩 8 秒，还要预留保存结果和清理时间；不能每次重试重置总预算。分别限制模型调用次数、输出 token、工具次数和总体耗时。客户端断开、任务取消、网络超时与业务回滚是不同事件。

取消先持久化请求，再停止新动作调度；执行中的操作需要底层支持、超时或隔离进程终止。协程的 `cancel()` 不是立即杀死所有底层工作；清理代码还要释放资源并正确传播取消。[Python 取消和超时语义](https://docs.python.org/3.13/library/asyncio-task.html#task-cancellation) 已提交的外部副作用不能靠取消撤销，要查回执、补偿或进入人工处理；未知 token 消耗保持 unknown。

**追问。** 把阻塞调用放进线程就能强制停止吗？取消与提交同时发生怎么定义结果？任务取消成功为什么不等于费用为零？

**动手与验收。** 运行 `python docs/interview/exercises/03_retry.py`，指出它只能停止后续重试、不能打断任意同步函数。为自己的实现保存三个时间线：执行前取消、执行中取消、已提交后取消；记录 request/ack/last-action 时间、最终状态与副作用数。用可控慢依赖验证取消后不发起新工具；若当前调用不能中止，要明确记录何时结束及资源归还，不能伪造即时取消。CaseDesk 的[任务持久化层](../../src/agentlab/desk/store.py)保存取消状态与执行代次，[引擎测试](../../tests/test_desk_engine.py)验证迟到 worker 不能再写回结果；这不等同于外部模型进程已经停止。

**常见失分。** 单个布尔标志宣称全链路取消；捕获所有异常后继续重试；把观测超时写成确定失败。来源线索：N02、N03。

## D05：改成 async，为什么服务还是崩了

**场景。** 诊断接口平均处理 5 秒；练习流量为每秒 20 个请求。接口快速返回 task ID，后台却不限量创建任务，队列越来越长。

**怎么推理。** 先假设系统稳定、接收的任务都能完成，且执行时间均值为 5 秒。由 Little's Law 可估算执行中的平均任务数约为 `L = λW = 20 × 5 = 100`，排队和重试会增加其他负担；这不是 100 个并发槽就够用的容量承诺。[Little 原始论文摘要](https://pubsonline.informs.org/doi/abs/10.1287/opre.9.3.383)

把函数改成 async 不会增加模型供应商配额或数据库容量。确定 worker 并发、队列容量、每租户公平性、下游配额和排队超时；队列满时按契约拒绝或稍后重试，不能无界积压。过载测试要同时观察可用吞吐与拒绝，避免快速拒绝把整体延迟“优化”得很好看。[AWS 负载削减实践](https://aws.amazon.com/builders-library/using-load-shedding-to-avoid-overload/) `asyncio.Queue(maxsize=0)` 也是无界队列；设置正上限会改变生产者等待行为。[Python 队列文档](https://docs.python.org/3.13/library/asyncio-queue.html)

状态保存在可恢复存储里，客户端轮询或 SSE 只是观察方式。连接断开不应重复创建业务任务；重连按任务 ID 与事件位置取状态。SSE 不能把“已接收”变成“业务成功”。

**追问。** 某租户占满队列时其他租户怎么办？两个 worker 怎么避免同时取同一任务？worker 死亡、租约到期和外部操作已成功如何协调？

**动手与验收。** 先运行[旧服务的 HTTP 冒烟](../projects/05-service.md)：`python scripts/smoke_service.py`；它验证流程，不是容量测试。独立写合成负载脚本，固定慢依赖、并发数、队列上限与时长，记录接收、拒绝、完成、超时、取消、排队耗时和健康探针结果。提交容量公式与实测偏差；过载后释放负载必须恢复，不允许靠清库恢复。无测试环境时交设计和未运行标记，不能填写虚构 P95。对照 CaseDesk 的[固定 worker 与入站限制](../../src/agentlab/desk/api.py)和[HTTP 契约测试](../../tests/test_desk_api.py)，把 API 接收、排队、实际处理分开验证。

**常见失分。** 只有平均延迟；只对成功请求计算耗时；无限重试造成二次流量；把 ThreadingHTTPServer 本身当作背压。来源线索：N03、N05、N06。

## D06：审核按钮通过，语义就可信了吗

**场景。** 资料写“配件齐全且无人为损坏时，14 个自然日内处理”。生成草稿只写“14 天内处理”。引用的来源是真的，但限制条件消失了。

**怎么推理。** 需要审核的是完整主张、条件、单位、适用对象和证据版本。界面同时给原文、引用位置与草稿差异，允许退回或修订。审核记录绑定草稿 version/digest、来源 revision、审核身份和有效期；任何相关编辑、权限变化或证据撤回都要重新判断有效性。模型自评可以帮助排序，不能冒充真人已经核对。

未审核的生成稿应停在待审；审核完成后有明确的继续路径，失败则留下理由和可修订状态。审批授权与语义质量还要分别检查：有权限的人也可能看漏条件。人工介入是系统过程，仍需抽查、负荷管理和质量数据。分层防护与人工控制的适用边界可参考 [OWASP](https://cheatsheetseries.owasp.org/cheatsheets/LLM_Prompt_Injection_Prevention_Cheat_Sheet.html)。

**追问。** A 审核后 B 改了正文怎么办？知识库更新但草稿没变怎么办？审核积压时可否自动放行？

**动手与验收。** 运行 `python -m unittest discover -s tests -p 'test_rag_pipeline.py' -v` 与 `python -m unittest discover -s tests -p 'test_workflow.py' -v`。参考测试展示引用与审批边界，不证明完整语义审核产品。独立交一张状态图和六个场景：缺失条件、篡改数字、证据过期、审核后编辑、撤回、重新审核后继续。验收必须包括拒绝和恢复路径；仅增加“待审核”字段不算完成。CaseDesk 的[审核与提交路径](../../src/agentlab/desk/engine.py)配合[HTTP 源版本生命周期测试](../../tests/test_desk_api.py)，可追踪修改、拒绝、重新审核和提交；测试审核人仍是模拟身份。

**常见失分。** 把审核人账号自动点击当真人审核数据；引用准确就当语义正确；只实现拦截而没有处理待办的流程。来源线索：N01 对质量证据的要求；本题审核业务由课程独立设计。

## D07：上游没收到回执，能否再提交一次

**场景。** 本地工单和 outbox 已提交，下游也创建了维修单，投递器在保存回执前崩溃。任务界面仍显示“投递中”。

**怎么推理。** 本地工单、幂等结果和 outbox 放进同一个数据库事务；投递到下游是另一个事务。崩溃后重放同一 event ID，下游依靠唯一约束与参数摘要返回原结果。重放不跳过鉴权；同键不同参数要冲突，不能静默覆盖。Outbox 解决本地双写窗口，仍可能重复投递，消费端必须处理重复。[AWS outbox 指南](https://docs.aws.amazon.com/prescriptive-guidance/latest/cloud-design-patterns/transactional-outbox.html)

业务幂等键应来自稳定操作身份，而非让模型每次生成随机字符串。去重记录保留多久、旧键过期后怎么办、同一业务能否合法再次发起，都要写契约。没有幂等或结果查询能力的外部接口可能留下不确定结果，需要人工核对。

**追问。** 把 HTTP 请求放在 SQL 事务里为什么不能获得跨服务原子性？“恰好一次”具体在哪个边界？删除去重记录以后还敢怎样重放？

**动手与验收。** 运行 `python docs/interview/exercises/04_idempotency.py`，再按[服务故障恢复](../projects/05-service.md)执行 `--crash-after-effect` 与重试。保留两边数据库计数、同 event ID 的两次投递、最终一份业务效果。故障开关应产生预期失败；不许为了让命令退出 0 删除失败分支。独立增加“同一键不同租户”和“同一键不同负载”的 HTTP 测试。CaseDesk 的[Store.commit / deliver](../../src/agentlab/desk/store.py)与[崩溃恢复测试](../../tests/test_desk_engine.py)给出同一模式在新应用中的落点，重点比较两个事务之间的未知窗口。

**常见失分。** “有 Redis 锁所以不会重复”；把消息投递一次当成数据库、邮件和所有外部系统都执行一次；超时就换新键。来源线索：N03 的重复触发、N07 的失败恢复；outbox 场景为课程设计。

## D08：接口成功率很高，为什么业务一直失败

**场景。** 查询接口 200 很多，任务却长时间待审；另一批返回 202 后再无结果。日志只打印“模型调用成功”，无法找到对应工单。

**怎么推理。** 分开记录 HTTP 接收、模型协议完成、任务终态、正确业务结果、人工验收。为同一任务串联 task/query/request/event ID，阶段 span 记录排队、检索、生成、校验、审核与投递耗时。重试尝试与业务动作分别编号；一次请求的 trace ID 不会自动串起以后几次独立请求。分布式追踪通过 span、父子关系和上下文传播连接操作。[OpenTelemetry traces](https://opentelemetry.io/docs/concepts/signals/traces/)

默认记录必要元数据和错误类别，限制正文与密钥进入遥测；trace ID 不能充当授权凭据。尾延迟要连同拒绝率、未完成量和超时阈值解释。若只报告成功完成样本，会隐藏慢任务和失败任务。

**追问。** 模型返回 200 但内容被截断怎么计数？排队耗时算进用户等待吗？追踪采样后还能声称完整统计账单吗？

**动手与验收。** 运行 `python -m unittest discover -s tests -p 'test_quality.py' -v`，定位“completed 但 task_success 为 false/unknown”的案例。独立交五条任务记录：正常、协议错误、语义失败、待审、超时未知。定义各指标的分子、分母和终态，要求每条业务动作能回到对应阶段记录；注入一个合成敏感哨兵，检查公开日志不出现它。性能报告另说明样本数量与采样设置。CaseDesk 的[事件与 metrics 实现](../../src/agentlab/desk/store.py)提供本地任务记录，尚不能因此声称完成了跨服务 OpenTelemetry 接入。

**常见失分。** 用模型调用成功率替代任务成功率；把未知用量记成 0；只给日志截图没有关联键和复现步骤。来源线索：N02、N06。

## D09：测试题全过了，换一份资料就不行

**场景。** 评测集来自 17 张事实卡的改写。调试时针对失败题补别名，改完仍在原测试集上报告“泛化提升”。

**怎么推理。** 按文档族、业务条件和任务类型分组，再划分开发/保留测试；同一事实的措辞变化不算独立知识。公开测试被用于调参后，就是已见回归集，不能继续叫盲测。数据泄漏的关键是本不应参与选择的信息影响了方案选择。[scikit-learn 数据泄漏说明](https://scikit-learn.org/stable/common_pitfalls.html#data-leakage)

比较时固定检索阈值、权限、语料时点、工具预算和打分规则，再单独改变待研究组件。分别报告证据覆盖、主张支持、答案完整性、错误放行、过度拒答、任务完成、延迟、成本与审核量。自动评分有适用边界：精确引用集合失败可能只是多引资料，也可能遗漏关键证据，需要逐题解释；模型裁判的偏差和人工复核分歧也应留下。

**追问。** 同一个模型造题再给自己评分会引入什么偏差？十条合成题的提升能推广到哪些任务？为什么不能边看测试答案边改阈值？

**动手与验收。** 阅读[真实模型实验](../experiments/local-model-run.md)及[数据规范](../projects/evaluation-dataset.md)，运行 `python -m unittest discover -s tests -p 'test_rag_eval.py' -v`。独立准备两个未见文档族，先冻结任务契约和数据 hash，再选参数。提交逐题结果、排除规则、失败分型及一个改变检索阈值的单变量对照。若已经看过保留集，就标成已见并另建下一轮保留集；不得删除难题抬高总分。CaseDesk 的[评测器](../../src/agentlab/desk/evaluate.py)与[评测契约测试](../../tests/test_desk_evaluate.py)提供新的综合案例入口；先读实际计分定义，再决定其能支持多大的质量结论。

**常见失分。** 一句“准确率 95%”没有分母；基线与新方案同时改变多个条件；把运行不报错当语义正确。来源线索：N01。

## D10：记住了聊天，为什么忘了用户的限制

**场景。** 用户最早说“只诊断，不提交维修单”。多轮后摘要保留了故障描述，却删掉该限制；后来同账号又切换到另一设备。

**怎么推理。** 分开存当前任务状态、会话历史、可选长期偏好和外部知识。权限、当前目标、明确限制、待完成事项、已提交动作及其回执必须有可验证的结构化状态，不能只藏在摘要中。摘要保存事实来源和可取回的原文引用；业务授权仍由服务端确认。跨会话记忆要明确用户/租户/任务作用域、保留期、删除与纠错方式。

按重要性构造上下文预算，把大工具结果存为带版本的 artifact，只加载当前需要的片段；保留近期原文可以帮助指代。是否压缩得好，要看约束保真与下游任务完成，不能只看 token 变少。[Anthropic 上下文工程](https://www.anthropic.com/research/effective-context-engineering-for-ai-agents)

**追问。** 一条旧偏好能否覆盖本次要求？撤回的知识会不会被摘要复活？A 用户的成功轨迹能否直接作为 B 用户的记忆？

**动手与验收。** 从[上下文章节](../chapters/06-memory-and-context.md)开始，独立构造 6 轮合成会话，包含否定限制、数字与单位、设备切换、撤回、未完成事项。提交压缩前后状态和三个追问的答案，要求能指出每个保留事实的来源；加入跨租户查询，必须拒绝。只交一段优美摘要不能通过。此题不要求把私人聊天放进仓库。

**常见失分。** 把全部历史永久入库；认为向量相似度能代替用户作用域；让检索出来的旧消息自动升级为执行授权。来源线索：N02、N03。

## D11：在自己电脑能跑，怎样让别人可靠接手

**场景。** 别人克隆项目后需要猜模型名、复制个人凭据才能启动；部署时换了容器，未完成任务和数据消失；恢复备份又重复投递。

**怎么推理。** 列清启动依赖、版本、配置、持久化目录、网络权限与可选模型路径。先有无需付费密钥的完整演示，再明确真实模型验证的前提与限制。提供 readiness、停写、排空、备份、迁移和回滚步骤，并验证恢复后的业务不变量。数据库文件在 WAL 模式下不能随意只复制主文件；使用受支持备份方法，另外核对多个系统的业务时点。[SQLite 备份 API](https://www.sqlite.org/backup.html)

容器封装不等于任意代码执行沙箱。模型可执行什么、可读哪些文件、是否能连网、资源上限和宿主接口都要界定；不要把 Docker socket、宿主根目录或生产凭据交给工具。[Docker 安全文档](https://docs.docker.com/engine/security/)

**追问。** 数据库新 schema 还能回滚旧代码吗？恢复本地备份后，下游已发生的效果怎么办？CI 测试通过和公开服务可用差在哪里？

**动手与验收。** 按[项目五](../projects/05-service.md)完成新路径备份恢复，运行 `python -m unittest discover -s tests -p 'test_backup.py' -v`。独立交一份 runbook，让另一个人从空工作目录复现；记录实际环境、失败与人工帮助。另交回滚演练：数据保留、旧审批处理、下游重放不新增效果。测试程序模拟的启动不能标成真人接手成功。

**常见失分。** 只给 Dockerfile；把本机标准库 HTTP 服务直接监听公网；删除数据库后重启宣称故障恢复。来源线索：N04、N06。

## D12：项目好用与有商业价值，怎么区分

**场景。** 系统能生成维修建议，却要求客服逐字核对，平均人工处理时间反而增加。项目报告只列模型费用，没有计审核、维护和失败重做。

**怎么推理。** 先定义使用者、重复任务和现有替代办法：搜索文档、表单、规则脚本或人工处理。选择一个窄任务，与现有方法做匹配对照，计算完成质量和人的净时间变化。单位完成任务成本可写为 `(推理 + 检索/存储 + 审核人工 + 失败重做 + 分摊运维) / 验收完成任务数`。失败与待审不能从成本中消失；本地推理也有设备和维护成本。

练习例子：100 个任务原本各耗 5 分钟；新系统全部要审核，各耗 2 分钟，另有 20 个要各花 4 分钟返工，则人工为 `100×2+20×4=280` 分钟，比基线少 220 分钟。这里只是算术示例；若正确性或风险变差，节省时间并不足以支持采用。

**追问。** 没有真实用户，能声称验证了需求吗？“愿意试用”与“愿意付费”有什么差别？客户为何不直接用已有工具？哪些维护成本会随着客户数增长？

**动手与验收。** 用[作品集模板](../templates/portfolio.md)记录目标、对照和本人贡献。独立提交一页价值假设、三类代表性任务、逐任务人工时间记录表、完整成本模型和继续/停止条件。先做合成技术实验，再经参与者同意开展匿名试用；记录真实反馈与实际付费证据的缺口。没有真实数据时保留空值和“待验证”，不能拿示例数字填成果。本课程首批试用对象是大学生：优先验证独立启动、定位失败、迁移新需求和答辩的学习效果，以及课程是否值得继续使用。CaseDesk 是综合工程案例；合成客服任务跑通，不能写成已有企业客户、实际节省客服成本或成交收入。

**常见失分。** 把功能数量、测试数量、GitHub star 或一次演示等同于需求验证；只统计最佳一次效果；写成实习线上项目却说不清用户和个人贡献。来源线索：N04、N07；价值模型为课程原创。

## 把答案变成一份可审查的提交

每次选择一题，在自己的练习分支提交实现与测试，或题目要求的实验/设计产物，再附简短说明；至少包含以下字段。它们是学习者需要填写的记录，不是已经完成的结果。

```text
场景与成功条件：
代码/数据版本：
先验假设与现有基线：
唯一主要改动：
正常任务与故障输入：
执行命令、实际结果、失败原因：
质量、等待时间、总成本、人工工作量：
个人负责部分、借用部分与许可：
仍然不能保证的事情：
```

先选一个需求做深，再扩展覆盖面。能够指出一项方案在自己的任务上不划算，并用证据保留更简单的方案，也是完整的工程判断。
