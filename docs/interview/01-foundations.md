# 01–10：基础与模型

[题库目录](README.md) · [下一组](02-tools-runtime.md)

## 01. 什么样的系统可以称为 Agent？〔入门〕

**直接回答：** 一个面向目标、根据观察选择动作、再根据执行结果调整后续行为的系统，可以采用 Agent 架构。工程讨论时要说明决策由谁负责：预设代码决定路径的是 workflow，模型动态选择步骤和工具的是一种常见的 LLM Agent。

**理由与取舍：** 同样是“查知识库后回答”，固定的检索与生成流水线已经足够。只有任务需要根据中途信息决定下一步时，动态决策的收益才可能抵消更高的成本、延迟和测试难度。[Anthropic 对 workflows 与 agents 的区分](https://www.anthropic.com/engineering/building-effective-agents)可作为术语参考。

**追问／得分点：** 对“请按已知规则计算运费”和“调查一次故障”分别选架构，并说明什么时候改变选择。

## 02. 一次工具调用与一个 Agent loop 有什么区别？〔入门〕

**直接回答：** 工具调用是一个动作；loop 管理动作前后的生命周期：获取上下文、请求决策、验证动作、执行、记录观察、判断是否继续。

**理由与取舍：** 模型给出工具名并不代表工具已经成功执行。运行时还需要处理未知工具、参数错误、超时与预算耗尽。把 loop 写成显式状态机，通常比递归地“再问一次模型”更容易定位问题。

**追问／得分点：** 画出一次超时后的状态变化；说明步数上限和工具超时分别控制什么风险。

## 03. ReAct 的核心思想是什么？〔入门〕

**直接回答：** ReAct 将任务推理与环境动作交替组织，让后续决策利用实际观察。它是一种决策与交互模式，不等于必须向用户展示模型内部推理。

**理由与取舍：** 静态计划可能在工具返回新信息后失效；观察驱动的调整能处理这种变化，但也会增加调用次数。工程日志应记录动作、参数、结果和简短决策依据，不需要把不可验证的长段自述当作审计证据。[原论文](https://arxiv.org/abs/2210.03629)研究了这种交替方式。

**追问／得分点：** 检索结果为空时，什么时候重写查询，什么时候停止并说明信息不足？

## 04. 为什么模型会给出流畅但错误的答案？〔入门〕

**直接回答：** 流畅性和事实正确性是不同目标。生成模型根据上下文预测后续内容，不能仅凭语言连贯程度证明某项事实存在。

**理由与取舍：** 错误也可能来自过期资料、检索缺失、工具误用或指令歧义。只调低温度不能修复错误数据；应把事实接到可查询的数据源，对关键输出进行确定性校验，并允许在证据不足时拒答。

**追问／得分点：** 将一次错误归因到检索、生成或业务数据，而不是统一称为“模型幻觉”。

## 05. Temperature 为 0 是否等于结果完全可复现？〔中阶〕

**直接回答：** 不应作此保证。较低温度通常减少采样随机性，但服务版本、数值计算、并发环境和上游工具结果仍可能改变输出；具体行为依赖供应商实现。

**理由与取舍：** 可复现实验应固定模型标识、提示版本、数据快照、参数、代码提交和工具响应。即使最终文本不同，业务结果也可能相同，因此应同时检查语义任务结果和运行轨迹。

**追问／得分点：** 如果两次文本不同但都创建了同一张合法工单，你会把哪一层判为不稳定？

## 06. Token、上下文窗口、输出预算之间是什么关系？〔入门〕

**直接回答：** Token 是模型处理文本等输入的计量单位之一；上下文窗口限制一次调用可处理的总体上下文；输出预算限制生成长度。不同模型对隐藏推理、缓存与多模态输入的计算方式可能不同，要查具体接口。

**理由与取舍：** 长历史、工具结果和检索片段都会挤占预算。按字符数估算只能用于粗略预警，正式计费与截断需要使用目标模型的计量方式。删掉早期消息可能同时删掉用户约束，必须保留约束和必要证据。

**追问／得分点：** 在预算不足时，你会优先保留用户授权、历史闲聊还是最新失败堆栈？说明规则。

## 07. Prompt engineering、RAG、微调分别改变什么？〔入门〕

**直接回答：** Prompt 改变当前调用的指令和示例；RAG 在运行时增加可检索证据；微调改变模型参数。三者解决的问题有交集，但不是可任意替换的选项。

**理由与取舍：** 经常更新的制度更适合外部知识源；稳定的输出格式或任务行为可以先用提示与验证，确有数据和重复需求时再评估微调。微调并不自动提供知识的来源追踪或访问控制。

**追问／得分点：** 面对“回答风格不一致”和“昨天的制度查不到”，分别提出第一步和验证指标。

## 08. 结构化输出为什么仍然需要业务校验？〔入门〕

**直接回答：** 结构正确只说明字段、类型等满足约定，不说明字段值真实、用户有权执行，或者操作符合业务规则。

**理由与取舍：** `{"amount": 100, "currency": "CNY"}` 可以完全符合 schema，但余额不足或请求主体不匹配。执行前要再次验证身份、资源归属、数值边界和状态版本。把这些检查交给提示词，会失去稳定的强制边界。

**追问／得分点：** 分清语法错误、业务拒绝与授权拒绝，并为它们设计不同错误码。

## 09. 什么时候应该使用小模型或规则？〔中阶〕

**直接回答：** 当任务边界清楚、错误代价可控、目标分布上已有证据表明其质量足够时，可以选择更便宜的模型或规则。需要按任务和失败成本做决策，而不是按参数量排名。

**理由与取舍：** 固定算术、权限判断和状态转移应优先由确定性代码承担。语义分类可以从简单基线开始；困难或低置信样本再升级。路由器本身也有误分成本，需要单独评测。

**追问／得分点：** 设计一个“规则→小模型→大模型”的升级条件，并解释总成本为什么不一定下降。

## 10. 怎样估算一个 Agent 任务的延迟和成本？〔中阶〕

**直接回答：** 按实际路径累加模型调用、工具调用和排队时间；并行分支的延迟由关键路径决定。成本要覆盖所有尝试，包括重试、失败任务和子任务。

**理由与取舍：** 若一次任务平均调用三次模型，不能只报最终回答的 token。应记录输入、输出、缓存计费单位和模型版本，并给出成功任务平均成本、总支出和 p95 延迟；重尾分布下均值会掩盖少量极慢任务。

**追问／得分点：** 一个并行方案延迟更低但总 token 翻倍，在哪种产品约束下值得采用？
