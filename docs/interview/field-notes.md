# 从面经线索到项目证据

[面试目录](README.md) · [十二个项目深挖场景](deep-dives.md) · [来源台账](../../data/interview-sources.json)

读面经最有用的动作，是把“别人被问过什么”改成“自己的代码能证明什么”。这里用公开牛客帖子发现准备盲点，再用技术文档、仓库代码和独立实验核查答案。下列场景与答案为课程原创，不是任何公司的原题或标准答案。

## 怎么使用

先完成[基础题](01-foundations.md)和[四道编程题](coding-exercises.md)，再选择一个深挖场景。第一次练习允许查资料；第二次关掉答案，用自己的项目解释，随后现场修改一个条件。

每次准备四样东西：一张数据流图、一条正常任务记录、一个能复现的反例、一份改进前后对照。没有实现的功能写进设计提案；没有运行的命令标记未运行；没有用户的数据不能包装成线上收益。别人的面经经历、公司名和结果不能写成自己的经历。

| 从资料中提取的准备方向 | 先练什么 | 交付物 |
| --- | --- | --- |
| 检索选型需要效果依据 | D01 检索失败归因、D09 评测 | 固定查询与语料版本的逐题对照 |
| 模型调用后仍有应用责任 | D02 决策边界、D03 工具校验 | 工具调用轨迹、被拒绝的越权提案 |
| 长任务不能只等待 | D04 取消、D05 背压 | 截止时间预算表、任务状态和过载实验 |
| 生成草稿要有人接手 | D06 语义审核、D07 可靠提交 | 审核版本、拒绝理由、重复投递证据 |
| 项目必须能排障和接手 | D08 追踪、D10 记忆、D11 交付 | 故障时间线、恢复记录、独立启动记录 |
| 技术收益要对应业务 | D12 价值核算 | 任务完成率、人工时间、完整单位成本 |

这些是课程的训练安排，不是帖子出现次数排名。每一项的具体题目、追问和验收见[深挖场景](deep-dives.md)。

## 从线索加工成原创练习

以 N01 为例，只提取“检索方式为什么有效”这个方向。课程另行构造一个维修知识库：型号要精确匹配，问法可能口语化，资料还会过期。练习比较固定条件下的检索结果，再解释增加向量检索或重排有没有实际收益。这个业务、测试数据、评分方式与答案都是重新设计的，不转录原帖问题序列。

来源记录与答案证据各管一件事：牛客链接解释为什么值得准备这个方向；官方文档核查接口和技术性质；本地实验支持“本项目做到了什么”。一种技术在文档中可行，不代表仓库已经实现；仓库已有测试通过，也不证明候选人独立掌握。

## 一场 45 分钟项目答辩

以下时间是练习安排，不是企业流程统计。

| 时间 | 面试官动作 | 候选人需要展示 |
| --- | --- | --- |
| 0–5 分钟 | 明确使用者、任务和限制 | 一句话说明问题、已有替代方案、个人负责范围 |
| 5–15 分钟 | 顺着一次任务问数据流 | 输入、检索、模型、工具、状态和最终业务结果 |
| 15–25 分钟 | 从 D01–D11 抽一个故障 | 先定位，再解释修复；不能靠改期望值让测试变绿 |
| 25–35 分钟 | 追加一个需求或边界 | 能现场改小范围代码，给出旧实现失败的新测试 |
| 35–42 分钟 | 追问收益与代价 | 固定版本的对照、失败样本、单位成本和人工投入 |
| 42–45 分钟 | 让另一人复述与接手 | 文档足以复现；明确未验证项和下一步 |

参考评分共 20 分：需求与取舍 4 分、实现与边界 4 分、失败定位 4 分、评测可信度 4 分、个人贡献与现场修改 4 分。每项 0 分表示无法解释，2 分表示能解释但证据不完整，4 分要求能展示并应对条件变化。该分数仅用于学习反馈，不对应录用概率。

准备完成的标志：另一个人换问题、换输入、打断任务后，你仍能解释代码和结果。不要以背会这十二个场景的答案作为终点。
