# 把学习项目讲成有证据的作品

[题库目录](README.md) · [项目目录](../projects/README.md)

简历写已经完成、能复现、能解释的工作。复制仓库后跑通示例，可以写学习和复现经历；只有自己做了明确的设计、修改或实验，才把对应部分写为个人贡献。

## 一页项目说明模板

```text
项目名称：
目标用户与问题：谁在什么情况下遇到什么困难？
实现范围：哪些路径已经可运行，哪些仍是设计？
个人贡献：具体修改了哪些模块，作出了什么决定？
数据来源：公开、合成或获授权数据；样本量、版本、切分方式。
架构：输入 → 决策 → 校验 → 工具／检索 → 输出或提交。
关键取舍：比较过哪些备选方案，选择依据是什么？
验证：运行命令、测试条件、基线、分母与失败案例。
结果：填写真实测量值；未测量则明确写“未测量”。
限制：尚未验证的模型、场景、并发、权限或部署条件。
复现：代码提交、环境、运行步骤与结果文件。
```

不要公开真实凭据、内网地址、个人账单、学校账户信息或真实用户对话。用合成数据演示流程，不把组织名称和个人信息当作项目真实性的装饰。

## 简历句式：动作、对象、证据、边界

可以使用的模板：

> 为［明确场景］实现［具体模块］，通过［机制］处理［失败问题］；在［数据集和条件］上相对［基线］得到［实测结果］，并保留［限制或失败案例］。

以下示例只有在自己完成并验证相应工作后才可以使用：

> 复现并扩展一个 Python 工具执行实验，实现参数校验、只读工具边界和有限步骤控制；为未知工具、无效参数与超时补充回归测试，并通过脚本化 planner 验证运行时行为。真实模型决策质量单独评测。

> 在合成知识库上比较词项覆盖阈值，记录可回答命中与不可回答拒答的取舍；保留同义表达漏检案例，并设计开发集选阈值、独立测试集复核的实验流程。

没有做扩展时把“复现并扩展”改为“复现”；没有创建新测试时删掉“补充”。不要把整个仓库的工作归为自己的贡献。

## 如何写指标

| 容易误导的表达 | 可核查的表达 |
| --- | --- |
| 准确率达到 95% | 在版本为 X 的 N 个任务上，按 Y 判定规则正确 n 个，比例为 n/N |
| 并发能力极强 | 在指定机器、到达率与负载模型下，p95 延迟为实测值，错误率为实测值 |
| 消除了幻觉 | 在所测不可回答子集上没有出现错误作答；样本量和范围明确 |
| 支持生产级安全 | 实现了具体权限检查与攻击测试；尚未验证的部署边界另列 |
| Agent 自主完成全部任务 | 列出动态决策、固定流程、人工审批分别负责的步骤 |

数据只有 8 条就写 8 条；没有线上用户就写离线合成任务。不要把离线 mock 的确定性成功率当作大模型能力。

## 90 秒项目答辩

**前 20 秒：** 用户是谁，为什么单次问答不能完成任务，哪些动作具有副作用。

**中间 40 秒：** 讲一条实际路径：用户问题如何变成工具提案；运行时检查什么；证据怎样引用；什么状态下需要审批；如何记录结果。

**接下来的 20 秒：** 讲一个失败案例与修复，例如审批后改参数导致旧令牌失效。指出测试文件或逐题评测记录。

**最后 10 秒：** 说明最重要的取舍与限制，例如“本地事务覆盖本地工单，外部工单系统仍需下游幂等与对账”。

## 五分钟演示顺序

1. 用干净环境运行一次成功路径，解释输出字段。
2. 输入一个明确不能处理的任务，展示拒绝或未完成状态。
3. 展示一条失败测试或故障注入，再看恢复结果。
4. 打开基线和候选方案的逐题差异，解释一项收益和一项代价。
5. 指出自己的改动与下一步实验，避免用计划中的功能冒充已实现功能。

面试官问“为什么不用某框架”时，先解释问题和约束，再解释框架能帮忙的部分与仍需自己负责的边界。不需要为了显得先进而否认简单方案。

## 项目完成后的交付物

一份可读 README、一条启动命令、一份数据说明、一个架构图、一项真实基线比较、一个失败复现、一个设计决策记录，通常比堆更多演示截图更能支持技术讨论。完整参考结构见 [综合项目](../projects/capstone.md) 与 [ADR](../projects/architecture-decisions.md)。
