# 岗位能力与作品集

[返回首页](../README.md) · [面试训练](interview/README.md)

Agent 相关岗位名称并不统一。阅读职位描述时先标注交付物：应用接口、检索系统、训练算法、推理平台，还是业务自动化。以下是能力划分，不代表招聘数量、薪资或某公司的统一要求。

| 方向 | 通用基础 | 本仓库重点 | 作品中值得展示的证据 |
| --- | --- | --- | --- |
| Agent / LLM 应用工程 | Python、HTTP、SQL、测试 | 工具、RAG、流程、安全 | 一条完整业务闭环及失败恢复 |
| 检索与知识工程 | 信息检索、数据处理、数据库 | RAG、上下文、评估 | 查询分桶、召回错误、权限过滤对照 |
| 模型与研究工程 | 线代、概率、PyTorch、实验设计 | LLM、评估、研究 | 可复现基线、训练细节、消融与误差分析 |
| 推理与平台工程 | 操作系统、并发、分布式系统 | 预算、生产、观测 | 吞吐延迟曲线、背压、取消和资源隔离 |

应用工程路线可以从三个项目起步。研究与平台路线需要额外学习训练框架、GPU/推理优化和分布式系统；本仓库提供问题入口，不能代替这些基础课程。

## 把职位描述拆成学习任务

假设职位要求“熟悉 RAG、工具调用和服务稳定性”，可以转换为三个验收题：

1. 在一组有答案、无答案和跨租户题目上比较检索基线，给出逐题证据。
2. 证明无效参数、未授权动作和重复请求在执行层被拒绝。
3. 模拟依赖超时，解释请求状态、重试预算和用户可见结果。

随后检查代码里能否定位到对应机制。简历每写一个术语，都应有可展示的实现或明确说明属于设计实验。

## 一份可信的作品集

README 说明任务和受众；架构图标出模型、工具、数据与授权边界；运行指南能让另一位同学重现；评估报告保存数据版本、配置和逐题结果；失败分析解释至少三类错误；设计记录描述没有选择的合理方案。

优先做一个完整项目，再补一个针对薄弱环节的小实验。数量多但运行不了、数据不清楚或回答不了追问的项目，难以支撑技术讨论。

## 自评分表

每项按 0–3 分自评：0 为无法说明，1 为能复述，2 为能实现，3 为能诊断和迁移。总分用于发现短板，不是录用预测。

| 能力 | 达到 3 分的证据 |
| --- | --- |
| 原理 | 能解释条件、反例和复杂度，而不只是术语 |
| 实现 | 干净环境可运行，重要不变量有测试 |
| 数据 | 数据来源明确，拆分合理，知道泄漏风险 |
| 评估 | 有基线、分母、重复实验及失败切片 |
| 安全 | 权限由服务端判断，攻击文本无法授予权限 |
| 系统 | 处理超时、重复、取消、恢复与版本变更 |
| 表达 | 五分钟说清任务、方法、证据和边界 |

## 五分钟答辩顺序

第一分钟讲问题和约束；第二分钟画关键路径；第三分钟展示一项实测对照；第四分钟讲失败和修复；第五分钟讲未解决的问题与下一步。准备好回答：样本从哪里来，为什么选这个基线，是否按成本公平比较，离线结果和真实用户有什么差距。

避免“用了某框架，所以具备生产能力”或“准确率达到某数字”而没有口径。更有信息量的表述是：在什么数据、什么任务、什么预算下，哪个指标变化多少，还有哪类题失败。未经实际测量的数字留空。
